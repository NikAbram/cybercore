Решения этапа 0 зафиксированы в `PROJECT_FOUNDATION.md`, каркас этапа 1 установлен и проверен, дизайн-система и графика этапа 2 описаны в `DESIGN_SYSTEM.md`, статические секции этапа 3 собраны из типизированных данных, взаимодействия этапа 4 реализованы и проверены. ## 1. Цель и границы MVP

Создать одностраничный русскоязычный сайт компьютерного клуба, который выглядит как полноценный коммерческий продукт: выразительный интерфейс, семь контентных секций, адаптивная навигация, тарифы, галерея, FAQ и отправка заявки администратору. Заявка является запросом на бронирование. Она не резервирует место автоматически и не подтверждает его доступность.

В MVP не нужны база данных, Prisma, CMS, личный кабинет, онлайн-оплата, учёт свободных ПК и отдельный backend. Контент размещается в типизированных файлах. На публичных страницах, в SEO-данных и сообщениях интерфейса не использовать слова «демо», «портфолио», «учебный проект» и похожие формулировки.

### Решения по уточнениям заказчика

- Кириллические заголовки и основной текст — **Inter**. **Space Grotesk** — для латинского логотипа, латинских названий зон и чисел. У Space Grotesk нет кириллического набора, поэтому русские заголовки не должны зависеть от случайной подмены браузером.
- Пока реальные сведения не готовы, для **закрытой предварительной версии** подготовить правдоподобные вымышленные контакты, цены, характеристики, режим работы и изображения. Хранить их в отдельных файлах с явным внутренним признаком черновика. После получения настоящих материалов замена должна выполняться в одном месте, без переписывания компонентов.
- Черновые данные не публиковать как подтверждённые сведения о действующем бизнесе. Не выбирать случайные реально работающие телефоны, адреса и почтовые ящики третьих лиц. Для визуального прототипа использовать безопасные нерабочие контактные значения. Не создавать вымышленные отзывы, рейтинги или разметку `LocalBusiness` с неподтверждённым адресом.
- Карта появляется только после подтверждения адреса. Турнир с датой, призовым фондом и кнопкой регистрации — только после подтверждения события и проверки ссылки. Пока событий нет, показывать состояние «Скоро новые турниры».
- Пока рассматривается только **Vercel Hobby**. Планировать на нём закрытую предварительную проверку, но не публичный коммерческий запуск: [правила Vercel ограничивают Hobby личным некоммерческим использованием](https://vercel.com/docs/limits/fair-use-guidelines). Перед публичным запуском потребуется отдельное решение по допустимому тарифу или хостингу.
- Если почтовый сервис не настроен или вернул ошибку, форма не показывает ложный успех. Формулировка успеха из ТЗ: «Заявка отправлена. Мы свяжемся с вами для подтверждения бронирования».

## 2. Стек и принципы

| Задача | Выбор | Обоснование |
|---|---|---|
| Приложение | Next.js App Router, React, TypeScript | Серверный рендеринг контента, SEO и API заявки в одном проекте. |
| Стили | Tailwind CSS, CSS-переменные | Быстрая адаптивная вёрстка без отдельной библиотеки компонентов. |
| Анимации | Motion (`motion/react`) | Небольшое число осмысленных анимаций с поддержкой `prefers-reduced-motion`. Не ставить параллельно Framer Motion. |
| Иконки | Lucide React | Единый набор лёгких SVG-иконок. |
| Форма | React Hook Form, Zod, `@hookform/resolvers` | Состояния формы и одна схема проверки на клиенте и сервере; resolver нужен для их интеграции. |
| Отправка письма | Route Handler и API выбранного почтового сервиса | Секреты остаются на сервере; при достаточном HTTP API использовать `fetch` без дополнительного SDK. |
| Качество | ESLint, Prettier, Vitest, Testing Library, Playwright | Проверки, указанные в ТЗ, и воспроизводимая приёмка. |
| Платформа предварительного просмотра | Vercel Hobby | Только в пределах допустимого некоммерческого применения; коммерческий релиз — отдельное решение. |

Ориентир по версиям на дату плана: [Next.js 16.4](https://nextjs.org/blog/next-16-4), [React 19.3](https://react.dev/blog/2026/09/09/react-19-3), Tailwind CSS 4.x и Node.js 24 LTS. Перед установкой проверить актуальные патч-версии, peer dependencies и предупреждения безопасности; зафиксировать рабочее сочетание в lockfile. Не добавлять глобальный менеджер состояния, Prisma, UI-kit, email SDK или другие пакеты без конкретной необходимости.

## 3. Архитектура и компоненты

```text
public/
  images/                  подготовленные изображения
  icons/                   favicon и статические иконки при необходимости
src/
  app/
    api/booking/route.ts   POST /api/booking
    privacy/page.tsx       утверждённая политика до приёма реальных заявок
    layout.tsx             общие metadata и шрифты
    page.tsx               главная страница
    sitemap.ts
    robots.ts
    globals.css
  components/
    layout/                header, мобильная навигация, footer
    sections/              hero, преимущества, зоны, тарифы, турниры,
                           галерея, контакты и FAQ
    booking/               диалог и форма заявки
    ui/                    только повторно используемые элементы
  data/
    site.ts                контакты, адрес, часы, ссылки и статус проверки
    zones.ts               оборудование, вместимость и преимущества зон
    pricing.ts             тарифы
    tournaments.ts         события и ссылки регистрации
    faq.ts                 вопросы и ответы
  schemas/booking.ts       общая схема входных данных
  lib/server/              конфигурация и отправка email
  lib/booking/             правила даты, времени и нормализации
  types/                   только действительно общие типы
tests/                     модульные и компонентные тесты
e2e/                       основные пользовательские сценарии
README.md
```

Главная страница и статические секции — серверные компоненты. Клиентские компоненты нужны только для мобильного меню, активного якоря, тарифного переключателя, галереи, диалога/формы и уведомлений. FAQ предпочтительно сделать на нативных `details/summary`, если проверка подтвердит нужное поведение. Не передавать серверную конфигурацию, email-ключи и лишние данные в клиентские компоненты.

Поток заявки: форма → клиентская проверка → `POST /api/booking` → ограничения запроса и серверная проверка → почтовый сервис → ответ интерфейсу. Положительный ответ сервиса означает, что он принял письмо к отправке; получение администратором проверяется отдельно тестовой заявкой. Приложение не сохраняет персональные данные в базе и не пишет их в логи.

Ограничить размер запроса, не раскрывать внутренние ошибки, не логировать ПДн, добавить простую антиспам-ловушку и реальное ограничение частоты запросов.

**Технологии:** React Hook Form, Zod, `@hookform/resolvers`, Route Handler, серверный API почтового сервиса; [Vercel WAF rate limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting), если доступен и соответствует условиям выбранного аккаунта. Счётчик только в памяти serverless-функции не считать достаточной защитой. **Skills:** `security-best-practices` — валидация, секреты, API, антиспам и ошибки; `vercel-react-best-practices` — граница server/client; `frontend-testing-debugging` — состояния формы и доступность диалога. **Готово, когда:** плохие запросы отклоняются сервером, успешная отправка подтверждена провайдером, ошибки понятны пользователю, статус брони не заявляется как подтверждённый.

## 6. Риски и недостающие требования

1. **Черновые сведения.** Их можно использовать для закрытой версии по решению заказчика. Перед публичным запуском проверить и заменить адрес, телефон, email, часы, цены, оснащение, фотографии, события, ссылки, SEO-текст и юридические сведения.
2. **Правила заявки.** Нужны часовой пояс клуба, доступные часы начала, глубина записи, длительности, вместимость зон, ограничения мест и трактовка стоимости пакетов. Без них нельзя закончить серверную проверку заявки.
3. **Персональные данные.** До приёма реальных заявок нужны утверждённая политика, текст согласия, сведения об ответственном лице или организации и проверка выбранных Vercel/почтового сервиса для обработки данных. Черновой юридический текст не считать утверждённым.
4. **Email.** Нужны выбранный сервис, настроенный домен отправителя, адрес администратора и тест получения. Без конфигурации форма честно сообщает об ошибке, не имитируя успех.
5. **Антиспам.** Honeypot и клиентская блокировка повторной отправки недостаточны сами по себе. Требуется проверенное ограничение частоты на стороне платформы или иного допустимого сервиса.
6. **Изображения и права.** Для закрытой версии можно собрать атмосферный визуал. Перед публикацией проверить лицензии и не выдавать абстрактные либо сгенерированные интерьеры за достоверные фотографии существующего помещения без согласования.
7. **Vercel Hobby.** Подходит к рассмотрению для предварительного использования в допустимых пределах. Публичный коммерческий запуск остаётся заблокированным до решения по тарифу или другой платформе.
8. **Производительность.** Наибольший риск для скорости создают hero, галерея и лишний клиентский JS. Результат оценивать по production-сборке; Lighthouse-баллы являются целями, а не гарантией.

## 7. Условия публичного запуска

- Черновые бизнес-данные заменены и проверены во всех секциях, форме, metadata и Open Graph.
- Адрес, карта, мероприятия, цены и характеристики соответствуют реальности; нет вымышленных отзывов или рейтингов.
- Политика и согласие утверждены, почта настроена, тестовая заявка действительно получена, секреты хранятся только на сервере.
- Ограничение частоты запросов проверено; API не сохраняет и не логирует персональные данные.
- Пройдены адаптивная, клавиатурная и визуальная проверки, компонентные и E2E-тесты, `lint`, `typecheck` и production build.
- Выбран тариф или хостинг, разрешающий публичное коммерческое использование.
